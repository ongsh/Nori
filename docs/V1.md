# V1 操作与验证范围

## 版本与授权

`init` 接收 JSON 规范并保存未批准版本；`approve --digest` 批准准确内容。模型输出没有用户审批入口。

变更规范先 `propose HOME --proposal ID --spec FILE --reason TEXT`，再用返回摘要调用 `accept-revision HOME --proposal ID --digest HASH`。旧要求、任务证据和失败运行保留。`accept-plan` 只接受不改变每个现有任务验收、目标、操作权限或总预算的调整；拆分、删除或更换验收需明确版本批准。运行未结束时不得替换输入。

默认每任务最多三次实现尝试，可在规范设 `max_attempts`；项目总预算为 `max_total_attempts`，省略则为所有任务上限之和。计划修订不清空历史次数。`max_seconds` 是执行硬预算，真实进程监督器独立执行，不依赖 CLI 一直在线。`max_output_bytes` 限制日志，按周期采样，终止前可能少量超出。

## 验收描述符

原有 `{ "R-01": "a.txt" }` 表示文件内容精确等于原要求文本。也支持：

```json
{
  "R-TEXT": {"kind":"exact_text","path":"a.txt","expected":"alpha\nbeta\n"},
  "R-JSON": {"kind":"json_value","path":"data.json","pointer":"/items/1/name","expected":"second"},
  "R-CHECK": {"kind":"command","operation":"synthetic-check"},
  "R-MANUAL": {"kind":"manual","prompt":"检查合成产物的显示结果"}
}
```

`operations` 将 operation 名称映射到已批准的固定 `argv` 数组、`timeout_seconds`、`max_output_bytes` 和可选 `generated_paths`。不接受 shell/env/cwd 替换或由执行者临时给出的任意命令。保存原始 stdout/stderr、退出码、超时和前后文件摘要。命令不是 OS 沙箱，批准操作时必须考虑其实际副作用。

`manual-binding HOME --requirement ID [--task TASK]` 给出当前内容绑定。用户实际检查后用 `manual ... --binding HASH --verdict PASS|FAIL --reason TEXT` 记录；旧绑定或没有明确检查不得放行。已停止但缺人工项的候选，可用 `retry-verification --task TASK` 重新取得验收许可，再 `verify --run-id RUN`。

若受控检查产生批准的生成物，可检查后用 `review-candidate --task TASK --digest WORKSPACE_HASH --reason TEXT` 固定当前候选，再重跑验收。超出允许范围的变化不会通过这个入口。

## 暂停、取消、恢复

`pause` 禁止新派发并请求当前适配器停止；`reconcile` 观察真实退出。`resume` 要求许可已安全收回。验收不确定但已停止的任务可 `rework --task TASK --reason TEXT`；次数仍受预算约束。

`cancel --reason TEXT` 和 `partial --reason TEXT` 在进程仍活动时只请求停止；再次确认退出后才能终止项目。部分成果被记录为 `CLOSED_PARTIAL`，不是 `COMPLETED`。

原子写入边界前崩溃保留旧完整状态，边界后保留新完整状态。缺失/损坏主状态时，`recover HOME` 只恢复有效备份并阻塞。`recover-review HOME --digest WORKSPACE_HASH --reason TEXT` 盘点所有模拟/进程运行回执；活跃、不明或无法匹配的运行仍拒绝解除。全部确认结束后清除过期验收并保持暂停，再由 `resume` 继续。

保存了 `PREPARED`、还没有调用保留记录和适配器回执时，`resolve-unstarted --run-id RUN` 可安全结束未启动尝试。已有启动意图却无可核对证据则不能这样猜测。

## 验收映射

- A-01~A-05：未批准、批准内容变化、前置未验、重复启动、旧结果均有合成反例。
- A-06~A-09：缺失文本/JSON 项、弱化验收、无进展提示与合理检查行为；没有宣称通用协议语义判断。
- A-10~A-14：越界、活跃进程恢复、半写入/缺失状态、暂停未退出、验收后文件变化。
- A-15~A-19：整体验收独立失败、人工缺项、保留已有文件、双工具共用运行约定/替身切换、次数/时间/日志预算。
- A-20~A-22：没有自动提交发布入口；同账户强隔离明确未满足；工作副本绑定和路径范围防误派。

本轮验证环境为 Linux，测试数据全部是临时合成文件/替身可执行程序。当前真实平台探测：Codex 0.167.0-alpha.4 报已认证，但合成启动失败于内部只读文件系统；Claude 未安装。因此真实双平台联调仍受环境阻碍，不能以契约测试替代它。

## 数据与故障边界

`state.json` 保存正式历史、需求/计划、运行、证据、决定和监督发现；`progress.md`、`acceptance-report.md`、`events.jsonl` 是派生视图。日志和运行回执位于控制目录，工作文件不混入私有配置。

调用者身份来自受信本地进程。没有提供一个接受 `actor: user` 就授予权限的网络 API。对可任意写控制目录的同账户程序不承诺防伪；需要强隔离时必须在正式接入宿主验证 OS/容器权限。
